背景逻辑：为什么是这个题

鸿蒙智能体应用开发的典型落地形态是"设备 + 场景 + 服务"的闭环。智慧客房把四类异构设备（温控、照明、遮阳、服务请求）压进一个竖屏 App，恰好覆盖 ArkTS 页面路由、状态驱动 UI、网络请求封装、Token 生命周期、动画与手势这些核心能力点。视频作为参照实现（golden sample）存在，意味着视觉还原度是可被比对的。

02核心要点

整体是"一号登录、四个 Tab、五类设备操作"。导航骨架固定为底部四页签：首页 / 灯光 / 窗帘 / 服务，登录页独立于外层。

登录页→首页（空调 / 场景 / 快捷服务 / 晚安）→灯光页→窗帘页→服务页→退出登录

2.1 登录与身份

  • 入参仅两项：roomNo、guestName，均必填且非空字符串；校验失败返回业务码 1001，账号不匹配返回 1002（"房间号或客人姓名错误"）。
  • 成功返回 token（JWT / HS256 / 12 小时）+ userInfo（房号、姓名、入住日期）。
  • 预置三组测试账号：1209 / 乔安、1210 / 张明、1211 / 李娜，入住日期均为 2026-05-26。
  • Token 必须持久化保存，冷启动时加载并自动恢复会话；收到 401（1101 无效 / 1102 过期）时清空本地 Token 并跳转登录页。
  • 登录页含"记住我的信息"勾选项（视频与预览图均有），默认勾选。

2.2 首页（信息中枢 + 高频操作）

区域要求
顶部标题"智慧客房"、"乔安，欢迎回家。"（姓名取自 token/userInfo）、右上角房间号胶囊
空调卡图标 + "运行中 / 已关闭"状态标签 + 电源键 + 减 / 目标温度大字 / 加 + 下方"当前温度：xx℃"；温度区间 16–30℃ 整数，步进 1℃
场景模式首页展示 4 张：明亮、柔和、阅读、温馨（选中态用主题色高亮）
快捷服务"请勿打扰""清理房间"两张卡，点击即切换，选中态高亮
晚安模式独立长卡"一键关闭所有灯光"，右侧闭合眼睑图标
全局操作结果以底部 Toast 反馈（如"已开启空调""已切换到柔和模式"）

2.3 灯光页（三种操作粒度并存）

  • 总开关：一键全开 / 全关。开时 9 个灯全部置 true，且 activeSceneId 被服务端设为 "bright"；关时全部置 false，activeSceneId 设为 "goodnight"。
  • 五个预设场景（灯光页独有的睡眠模式在此）：
场景 ID名称点亮的灯具
bright明亮模式全部 9 盏
soft柔和模式落地灯、左阅读灯、右阅读灯
reading阅读模式左阅读灯、右阅读灯、书桌灯
cozy温馨模式落地灯、吧灯
sleep睡眠模式廊灯
goodnight晚安模式（隐藏）全部 9 盏关闭，等价"一键全关"
off退出场景（隐藏）不动灯具，仅清空 activeSceneId
  • 9 盏独立灯具，顺序与 UI 一致（2 列布局）：洗漱间、衣柜灯、落地灯、吧灯、左阅读灯、右阅读灯、书桌灯、排风扇、廊灯。单灯操作后 activeSceneId 恒为 null（视为自定义状态），masterLight 按"任意灯亮即 true"重算。

2.4 窗帘页（唯一需要客户端做动画的模块）

  • 两组：布帘 cloth、窗纱 sheer；顶部"全部打开 / 全部关闭"批量操作。
  • 单组三按钮：打开 / 暂停 / 关闭，动作与状态严格区分——动作 open/pause/close，状态 opened/paused/closed。
  • 后端不模拟运动过程：收到动作即把状态置为目标值，开合动画必须由客户端实现，包括中途暂停停在中间位置的效果。
  • 批量接口只支持 open 与 close，不支持 pause。

2.5 服务页

  • "请勿打扰""清理房间"两个独立开关（可同时开启），各自有开 / 关状态。
  • 右上角红色 SOS 按钮：一次性事件触发，无状态、无参数；服务端仅打印警告日志，不对接真实前台。
  • 底部"退出登录"描边按钮：服务端无状态、不作废 Token，客户端必须自己清空本地 Token 与用户信息。

2.6 数据与状态模型（决定架构）

核心是"一个快照接口点亮整页"的读模型：GET /api/room/snapshot 一次性返回 room / ac / scenes / activeSceneId / masterLight / lights / curtains / services 八块。首页进入调一次，子页面进入再调一次，各取所需字段。房间号由 Token 解析，客户端不传参。

写操作全部是"命令 + 返回受影响对象"，客户端需用返回值刷新局部状态，而不是盲目乐观更新——因为服务端会做联动（如场景切换同时改 9 个灯与总开关）。

3.1 统一响应与双层判定

所有接口返回 Result<T>：{ code: number, msg: string, data?: T }。业务成功码是 0，不是 200；客户端必须两层判断——先看 HTTP 是否 2xx，再看 code 是否 0。文档明确要求 msg 仅用于 Toast 或调试，不得用于业务判断。

业务码HTTP含义客户端处理要求
0200成功取 data 使用
1001200参数错误（缺字段 / 类型不符 / 越界 / 非法 JSON）Toast 错误消息
1002200房间号或客人姓名错误仅登录接口，提示重输
1003404接口不存在检查路径与请求方式
1101401Token 无效（缺失 / 格式错 / 签名错）清空本地 Token，跳登录页
1102401Token 已过期同上

1202200设备繁忙（保留码，Mock 未触发）Toast"操作太快，请稍后重试"
5000500服务器内部错误Toast 通用错误提示

3.2 视觉与交互规范

  • 竖屏单列布局，浅色玻璃拟态卡片（半透明 + 模糊）叠在客房实景背景图上；主色为橄榄绿/灰绿（#8a9a5b 量级），选中态用主色实底 + 白色文字/图标。
  • 底部固定四页签，选中项为椭圆形主色胶囊包住图标 + 文字。
  • 统一交互反馈：操作成功 → 底部胶囊 Toast；数据请求中 → 居中"加载中…"转圈遮罩（视频服务页可见）。
  • 素材来自"鸿蒙智慧客房应用-UI素材包"（图标、背景、窗帘贴图），预览图提供 9 张状态稿：00登录 / 00登录_fill / 01首页 / 01首页_act / 02灯光 / 02灯光_act / 03窗帘 / 03窗帘_opening / 04服务，_act 为选中态、_opening 为开合过程中间帧、_fill 为填写态。

04限制条件

约束具体规定与影响
后端不持久化所有房间状态存内存，重启即还原默认快照。持久化是客户端的考点，不是后端职责。同时意味着多次联调互不污染。
登出不作废 Token/api/auth/logout 无状态、不维护黑名单，Token 在 12 小时内仍可用。客户端必须自行清理本地存储并跳转。
温度边界目标温度必须为 整数且 ∈ [16, 30]，越界返回 1001；minTemp/maxTemp 固定 16/30，不可改。
温度模拟currentTemp 由后端每秒 0.5℃ 向 targetTemp 逼近，仅开机时；关机保持不变。客户端反复拉快照才能看到连续变化。
隐藏场景goodnight 与 off 不出现在 scenes 列表，仅可作为 POST /api/light/scene 的入参；off 不会出现在 activeSceneId 中。
场景会覆盖手动态任何场景切换都会按预设重排 9 盏灯；单灯操作会把 activeSceneId 清零。二者互斥，客户端高亮逻辑必须跟随服务端返回值。
批量窗帘限制只接受 open / close，pause 在批量场景无意义、会被拒。
窗帘无位置量接口只给三态，没有 0–100 的位置字段，暂停位置只能由客户端本地记录并自行绘制。
SOS 无状态一次性事件，服务端不保存"求助中"状态，客户端不能靠快照判断 SOS 是否已发出。
素材与后端不可改后端与 UI 素材由命题方提供，用于联调与还原；视频为效果参照。
保留错误码1201/1202 在 Mock 后端不会触发，属于"预留但当前不可测"的分支。

06模糊、缺失与冲突清单

以下问题在现有材料中无法得到唯一解释，实施前需要命题方澄清或自行决策并记录假设。高 表示会直接影响实现路径或评分。

编号问题级别说明与建议
Q1技术文件整体缺失高 评分权重、竞赛时长、模块划分、提交物清单、违规与扣分规则全部未知。现有材料只能推出"功能 + 视觉"两维，无法推出配比。建议先补齐该文件再定排期。
Q2首页场景卡数量冲突高 接口 scenes 返回 5 个（含睡眠），但首页与预览图只展示 4 个（明亮/柔和/阅读/温馨），睡眠模式只出现在灯光页。究竟是"首页故意裁掉睡眠"还是"应全量渲染"，无明文。建议按视频实现（首页 4 个），并在说明中记录。
Q3温度大字含义易混中 视频与预览图中大字 20–22℃ 实际是 targetTemp，小字才标注"当前温度"。而 AcState.currentTemp 才是实时值，字段名与视觉主次相反，实现时极易接错。建议以 targetTemp 驱动大字。
Q4masterLight 语义漂移中 快照里它是"灯光总开关状态"，但单灯接口返回的 masterLight 定义为"任意灯亮即 true"。同一字段在两条链路上含义不同，客户端不能把它当作"用户是否按过总开关"来渲染。建议 UI 只用它做视觉态，不做逻辑判断。
Q5暂停位置无数据支撑中 窗帘只有 opened/paused/closed 三态，无位置百分比。暂停后重进页面，服务端只说"paused"，无法还原停在哪。客户端只能本地缓存位置；而服务重启后状态又回到 closed，与本地缓存冲突。建议本地缓存以服务端三态为准做校正。
Q6goodnight 会成为不可见的选中态中 关总开关后 activeSceneId = "goodnight"，但该值不在 scenes 列表里。客户端若按列表匹配高亮，会出现"有选中态但无卡片高亮"的空档。需专门处理：映射到首页"晚安模式"卡的高亮。
Q7off 的触发入口未定义中 文档只说 off 用于"首页晚安卡片重复点击时取消高亮"，但未规定：再点一次是否调 off、灯是否保持全关、Toast 文案是什么。建议实现为切换式。
Q8两个服务开关的互斥性低 接口明确"相互独立，可同时开启"，但业务上"请勿打扰"与"清理房间"语义冲突。是否需要客户端做互斥提示，无规定。建议不做限制，保持与接口一致。
Q9SOS 交互流程缺失中 仅有"红按钮 + 一次性事件"。是否需要二次确认、倒计时、可取消、防重复点击、成功后的视觉反馈，全部未定义；视频中也未演示 SOS 点击效果。建议加二次确认 + 成功 Toast。
Q10"记住我的信息"与 Token 的关系低 接口文档只要求持久化 Token，未规定勾选框控制什么（房号姓名？Token？两者？）。建议：勾选存账号 + Token，不勾选只存 Token 于内存。
Q11保留错误码是否需实现低 1201/1202 在 Mock 后端不会触发，无法验证。建议实现分支但标注"不可测"。
Q12交付路径表述不一致低 接口文档说客户端项目与 smart_hotel_server/ 平级；后端 README 却说接口文档"与 Code/ 目录同级，位于 Product/ 下"。两者描述的目录层级不吻合，需以赛场实际结构为准。
Q13文件格式异常中 技术文件扩展名为 .docx，实际为 OLE2（Word 97-2003）二进制，内嵌 WPS 元数据。Word 直接打开可能报"文件格式与扩展名不符"，建议改名 .doc 或用 WPS 打开后另存为标准 docx。
Q14视频信息量受限低 113.7 秒、496×1066 竖屏录屏，无音轨、无旁白、无字幕。仅演示了正常路径，未覆盖：登录失败、Token 过期、网络异常、温度边界、单灯操作、睡眠模式、SOS 点击。这些只能从接口文档反推。
Q15登录校验规则未细化低 未规定房号是否限数字、长度、是否 trim、姓名是否区分大小写与空格。Mock 后端按字符串精确匹配，客户端建议原样提交并 trim 首尾空格。
